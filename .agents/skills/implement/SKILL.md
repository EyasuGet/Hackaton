# Implement one approved issue

Start from a fresh session with the issue, not the design conversation. Read [AGENTS.md](../../../AGENTS.md), the selected [local issue](../../../docs/issues.md) (or authoritative GitHub body after migration), its parent/shared spec and relevant architecture decisions.

## Before changing code

1. Confirm implementation was requested, the selected item is an approved/claimed leaf task (not an epic), its parent acceptance has been read, and its explicit dependencies/prerequisites are complete. If the leaf has grown beyond one focused outcome, propose child slices before implementing an oversized PR. Baseline phases are milestones, not waiting barriers. Apply the backlog’s leaf priorities and core/full-brief gates: shared parent safety rules apply, but deferred sibling features are not hidden prerequisites for core leaves. If blocked, follow [the blocked-work procedure](../../../docs/issues.md#when-work-is-blocked) and select other ready baseline work; do not invent a missing dependency or waive live acceptance. Respect existing work and another owner's claim. A spec-writing request is not implementation approval.
2. Inspect current behaviour, callers, shared contracts, relevant earlier implementations, tests, configuration, and Git state. Reuse established behaviour and account for the applicable overall spec/decisions, not only the current issue. Once Git exists, use an issue branch into `main` according to the user's action authorisation; do not initialise/publish a repository as a side effect. If the issue depends on repository setup that has not happened, report that prerequisite.
3. State the smallest adequate implementation plan and the issue's proving check. Apply [the coding standards](../../../docs/coding-standards.md): reuse suitable existing code, and justify any new abstraction/dependency by a present requirement, not hypothetical flexibility. Reopen only unresolved choices that change agreed scope, interfaces, privacy, cost, external dependencies, or acceptance. Ordinary internal decisions stay with the implementer.
4. For a consequential unfamiliar model/provider/library choice, verify current primary documentation and evaluate against the feature's language quality, correctness, accessibility, portability, failure behaviour, latency, and cost constraints. Record dated evidence/alternatives in the relevant issue or shared decision record. Existing supported choices need not be re-researched on every edit. A benchmark or marketing claim is not proof for our Amharic/device use case.

## Build and verify

5. Run relevant existing checks before editing and preserve the results. Apply [the test-writing rules](../../../docs/verification.md#test-writing-rules): identify the distinct risk, inspect existing coverage, choose the lowest sufficient layer, and justify deliberate cross-layer overlap. Every new test must assert its named behaviour; regression tests should fail without the fix. No runnable project yet means foundation checks are planned, not passed.
6. Implement the narrow vertical slice. Follow feature-first Clean Architecture and [the coding standards](../../../docs/coding-standards.md) for TypeScript, useful file/block/line comments and efficient execution; introduce only required layers, classes, dependencies, and tests. Run the focused checks while iterating. Obtain exact commands from package scripts/README/CI, not a generic tool recipe.
7. A correction to an unexpected failing check that alters assertions, fixtures, error handling, concurrency, retries, or externally visible behaviour needs a blind [fix-guard](../../agents/fix-guard.md) pass. Preserve the first failure, pre-fix snapshot and complete fix diff. Planned red-first tests are not a failed-fix round. The guard receives failures, diff, relevant spec, and necessary raw code/evidence—not the implementer's rationale. After three rejected correction rounds, stop and hand back the unresolved cause rather than looping or weakening the check.
8. Run documented pre-PR checks, inspect the final diff, and account for every acceptance criterion. Capture real external/device evidence where required. A mocked integration, skipped check, or missing credential remains explicitly unverified/blocked.

## Review and hand off

9. The author follows [code-review](../code-review/SKILL.md), using independent standards/spec AI reviewers rather than waiting for a teammate PR reviewer. Check compatibility with the current main branch, affected callers/shared contracts and applicable overall decisions. Fix blocking findings; rerun affected checks and re-review material changes. Reviews and evidence must identify the same candidate revision; a changed candidate is not covered by an older pass.
10. The PR author completes [the template](../../../.github/pull_request_template.md), including test rationale, compatibility evidence, review findings and the author merge checklist. The author may sign off and merge their own PR; another teammate's approval is not required by this workflow. Sign-off means the template checklist, not a GitHub Approve review on one's own PR. If actual branch protections require an independent approval, raise the configuration conflict with the maintainer rather than bypassing it. Refresh/check main through authorised Git operations before merging; if it advanced, inspect the delta and revalidate the integrated candidate, including material conflict resolutions. Satisfy actual branch protections and CI; do not bypass them. An agent commits/pushes/opens/merges only within the user's action authorisation; otherwise leave the local diff and PR draft. Author-led merge does not waive required co-designer/device evidence.
11. Report files changed, why new files/helpers/tests are necessary, checks passed/failed/unrun, reviewer verdicts, outstanding blockers, and the human Verify story. Close the issue only after merge and integrated acceptance evidence through the authorised tracker workflow.
